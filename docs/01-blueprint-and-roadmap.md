# 后端求职向 C++ 游戏项目：蓝图与路线图

> 目标读者：在校学生，目标岗位 = 后端工程师（含游戏服务端方向），本项目是**求职主项目**。
> 结论先行：**做"多人在线游戏的服务端"，客户端做到"能玩就行"。**

---

## 1. 一句话方案

用 **C++20 写一个房间制回合卡牌对战的服务端**（自研 epoll 网络层 + actor-per-room 调度 + MySQL/Redis 持久化 + 网关/匹配拆分 + 压测报告），
客户端先命令行、后网页 WebSocket。**服务端是作品，客户端是脚手架。**

这不是"做个游戏玩玩"，而是**用一个有真实业务语义的系统，把后端面试要考的每一块都练到并留下证据**。

---

## 2. 为什么必须是"多人服务端"，而不是单机游戏

| 作品形态 | 能证明什么 | 对后端岗的价值 |
|---|---|---|
| 单机游戏（SDL/UE/图形） | C++ 语法、图形 API、游戏循环 | 低。面试官看到的是"会写 C++ 的学生作业" |
| 纯后端 demo（增删改查 API） | 框架会用 | 中。和几千份课程作业无法区分 |
| **多人游戏服务端** | 网络编程、并发模型、状态一致性、持久化、扩展性、可观测性 | **高**。每一条都是后端面试的正面考点 |

关键洞察：**游戏服务器就是最难的一类后端**——长连接、有状态、低延迟、强一致、要防作弊。
把它的复杂度压到个人能完成的规模，你就拿到了一个"讲不完"的项目。

⚠️ 但要警惕反面：如果做成 FPS / 3D 实时物理对战，你的 90% 时间会烧在客户端同步和美术上，后端反而没深度。**规则要简单，网络要真实。**

## 3. 推荐玩法：回合制卡牌对战（极简版）

### 规则草案（够用就好）
- 双方英雄 30 点血，牌库 20 张，手牌上限 5，每回合 1 点费用。
- 卡牌 12~20 种：随从（攻/血）、法术（伤害/抽牌/治疗）、装备（可选）。
- 回合流程：`抽牌 → 出牌/攻击（可多次）→ 结束回合 → 对方回合`。
- 胜负：一方血量 ≤ 0，或牌库抽空（疲劳）。

### 为什么这个玩法最适合"求职向"
| 后端考点 | 这个玩法天然覆盖 |
|---|---|
| 会话与房间 | 登录 → 匹配 → 进房 → 开局 → 结算 → 退房，完整生命周期 |
| 状态机 | 房间状态机（等待/匹配中/对战中/结算）、回合状态机，天然要画状态图 |
| 指令校验 | 客户端只发"意图"（我要出第 3 张牌打对面英雄），合法性全在服务端判定 → **服务端权威**天然成立 |
| 确定性 / 重放 | 随机数用服务端种子 + 指令日志，可完整回放整局 → 录像、复盘、反作弊一箭三雕 |
| 断线重连 | 快照（当前局面）+ 增量（断线期间的指令）即可恢复，比实时游戏简单一个数量级 |
| 匹配与天梯 | 排队、分段匹配、Elo/积分、排行榜 → Redis 场景 |
| 持久化 | 账号、卡组、战绩、赛季积分 → MySQL 事务 + 索引 |

### 备选玩法（如果你不喜欢卡牌）
- **B. 实时 IO 类**（贪吃蛇/坦克混战）：强在 tick 循环与快照插值，弱在规则太薄、客户端工作量大。适合作为**第二个项目**。
- **C. 合作塔防/轻 MMO**：覆盖最全，但周期翻倍，个人项目容易烂尾。
- 判定标准只有一条：**规则能否在 2 周内写完并单测通过？** 能，就选它。

## 4. 架构设计

### 4.1 目标架构（终态）

```
┌──────────┐   WebSocket / 自定义TCP    ┌───────────────────────────┐
│ 客户端    │ ─────────────────────────► │ Gateway 网关               │
│ (Web/CLI)│ ◄───────────────────────── │ 连接管理 / 心跳 / 限流 /   │
└──────────┘                            │ 编解码 / 会话路由          │
                                        └────────────┬──────────────┘
                                                     │ 内部 RPC
                     ┌───────────────────────────────┼──────────────────┐
                     ▼                               ▼                  ▼
            ┌─────────────────┐            ┌─────────────────┐  ┌──────────────┐
            │ Room 服务        │            │ Match 匹配服务   │  │ Account 服务  │
            │ 每房间一个 actor │            │ 排队/分段/段位   │  │ 登录/卡组/战绩│
            │ 串行执行，无锁   │            └────────┬────────┘  └──────┬───────┘
            └────────┬────────┘                     │                  │
                     │                              ▼                  ▼
              ┌──────┴───────┐              ┌────────────┐     ┌─────────────┐
              │ 定时器轮/事件 │              │   Redis    │     │   MySQL     │
              │ 异步落库队列  │              │ 排行榜/在线 │     │ 账号/战绩    │
              └──────────────┘              └────────────┘     └─────────────┘
```

### 4.2 关键决策：**先单进程，后拆进程**

个人项目最常见的死法：第一周就上微服务，最后死在运维上。

```
v0.1  单进程单线程        → 跑通玩法逻辑（纯逻辑库，零网络）
v0.2  单进程 + Reactor IO 线程 + 业务线程池 + 房间 actor
v0.3  单进程 + MySQL/Redis（异步落库）
v0.4  拆出 Gateway 与 Match 两个独立进程，自研极简 RPC 通信  ← 面试讲"演进"比讲"终态"加分
```

**演进过程本身就是简历素材**："我先单进程验证玩法，压测发现 IO 与业务互相阻塞，于是拆出独立 Reactor 线程 + 房间 actor 模型，P99 从 xx 降到 xx。"

### 4.3 线程模型（面试必讲）

- **IO 线程**（1~N 个）：`epoll` ET 模式 + 非阻塞 fd，只做读写与解包，不做业务。
- **工作线程池**：处理与房间无关的轻任务（登录校验、匹配计算）。
- **房间 actor**：每个房间绑定一个逻辑执行流，所有房间消息投递到房间自己的 SPSC 队列，串行处理 → **房间内零锁**。房间之间无共享状态。
- **定时器线程**：时间轮（time wheel）管心跳超时、回合倒计时、匹配超时。
- **落库线程**：批量异步写，房间逻辑线程绝不碰 DB。

一句话卖点：**"单进程多线程，但共享状态最小化；房间内串行，房间间并行。"**

## 5. 技术选型

| 领域 | 选择 | 为什么 | 替代 |
|---|---|---|---|
| 语言标准 | C++20 | `coroutine`/`span`/`concept` 可讲，岗位主流 | C++17（保守） |
| 构建 | CMake + Ninja | 事实标准，面试会问 | xmake |
| 依赖管理 | vcpkg（或 CMake FetchContent） | 别手搓下载脚本 | conan |
| 网络 | **自研 epoll Reactor** | 这是本项目最值钱的练习，别用库糊过去 | Asio/libevent（可做对比实验） |
| 协议 | 自定义二进制（长度+cmd+payload），后期加 protobuf 对比 | 讲清楚取舍就是加分项 | 全 protobuf |
| 编解码 | 手写 buffer + 变长整数（varint） | 面试常问粘包/零拷贝 | flatbuffers |
| 数据库 | MySQL 8（Docker） | 事务/索引/隔离级别考点 | PostgreSQL |
| 缓存 | Redis 7（Docker），**自研极简 RESP 客户端** | 自己实现协议 = 亮点 | hiredis |
| 日志 | spdlog，或自研异步 ring buffer 日志 | 前者省时，后者是面试点 | glog |
| 测试 | GoogleTest + CTest | 有单测的学生项目是少数 | Catch2 |
| 压测 | 自研 C++ 压测客户端（可控并发与消息模式） | 能造出真实数据写进简历 | wrk / k6 |
| 监控 | Prometheus `/metrics` + Grafana 面板 | 有监控截图 = 工程感 | 自研 HTML 面板 |
| 部署 | Docker Compose（server + mysql + redis + prometheus + grafana） | 一条命令起环境 | 裸机脚本 |
| CI | GitHub Actions（Linux runner 编译 + 单测 + clang-format） | 绿标 + badge | GitLab CI |
| 客户端 | 阶段1 终端 CLI（关键路径） → 阶段2 **Godot 4.5 薄壳**（周末支线） | 见 [ADR 0002](adr/0002-godot-client.md)，有 70h 硬上限 | 网页 HTML+Canvas（止损备选） |

### 环境现状（你这台机器，已探测）

| 已有 | 缺失 / 注意 |
|---|---|
| MSYS2 UCRT64 `g++` | **没有 cmake、没有 cl（MSVC）** |
| `ninja`、`git`、`python`、`node` | 无 vcpkg / conan |
| Docker Desktop | Docker 可用 → 跑 MySQL/Redis/Prometheus 没问题 |
| WSL 已安装（探测被沙箱拒绝，未能列出发行版） | — |

**建议：服务端主体在 WSL2 Ubuntu 里开发**（`apt install build-essential cmake ninja-build clang-format`）。
原因：`epoll` 只在 Linux 存在，而 epoll 是这个项目的核心卖点；Windows 侧留着写文档、看客户端。
如果你想让服务端也跑在 Windows 上，就把 `Poller` 抽成接口，Windows 实现用 IOCP —— 这是**额外加分项，但不建议第一版做**。

## 7. 怎么拿到简历上的"真实数字"

简历里写"支持 5000 连接"却答不出怎么测的，是减分项。做法：

1. **固定测试条件**：单机 4C8G、Linux、`ulimit -n 100000`、关闭日志 debug 级别。
2. **阶梯加压**：100 → 500 → 1000 → 2000 → 5000 连接，每档稳定 3 分钟。
3. **记录**：连接成功率、在线峰值、msg/s、平均/P95/P99 延迟、CPU、内存、峰值 fd 数。
4. **找瓶颈**：`perf top` + 火焰图，明确说出"瓶颈在 X，我改成了 Y，P99 从 A 降到 B"。
5. **报数原则**：只报**你实测过并且能复现**的数字；写清测试环境与工具。

> 简历上每出现一个数字，都要能回答："怎么测的？瓶颈在哪？怎么优化的？"

## 8. 简历与面试

### 8.1 简历条目模板（用实测数据填空，**不要编**）

> **C++ 多人在线卡牌对战服务端**（个人项目，C++20 / epoll / MySQL / Redis / Docker）
> - 自研 epoll ET Reactor 网络层与长度前缀二进制协议，处理粘包/半包与心跳超时；单机稳定支撑 ___ 并发长连接、___ msg/s，P99 延迟 ___ ms。
> - 采用 actor-per-room 串行调度 + 无锁 SPSC 队列，房间内零锁竞争；相比初版全局锁，P99 由 ___ ms 降至 ___ ms。
> - 实现快照 + 指令日志的断线重连与全局回放；所有客户端指令经服务端权威校验与速率限制，可抵御越权出牌/重放攻击。
> - MySQL 异步批量落库 + 连接池，Redis 承载排行榜与在线状态；登录链路 QPS ___，落库对战斗延迟影响 < ___ ms。
> - Docker Compose 一键部署，Prometheus + Grafana 监控连接数/延迟/错误率，GitHub Actions 跑编译与单测。

### 8.2 一定会被追问的题（提前准备答案）

- **网络**：epoll ET vs LT、水平触发的坑、惊群与 `SO_REUSEPORT`、accept 负载不均、C10K→C1000K、TCP 粘包本质、为什么不用 UDP（本题：回合制不需低延迟，但要可靠有序）。
- **并发**：为什么房间 actor 比全局锁好、内存序与 `memory_order` 何时需要、伪共享、线程池任务窃取要不要做、定时器为什么用时间轮而不是 `sleep` 排序。
- **C++**：对象生命周期与 RAII、`shared_ptr` 循环引用与性能代价、移动语义、`unordered_map` 扩容与 rehash 抖动、内存池解决什么。
- **数据**：走索引与不走索引的差别、事务隔离级别与幻读、为什么落库必须异步、Redis 用哪种结构做排行榜（zset）与持久化取舍。
- **架构**：为什么单进程够用、拆分带来什么代价（网络调用、超时、一致性）、如何水平扩展（房间分片 + 网关无状态 + 一致性哈希）、线上 CPU 100% 怎么排查。
- **游戏特有**：状态同步 vs 帧同步（讲清本题为何选前者思路）、服务端权威与作弊面、回放如何保证确定性。

### 8.3 讲法准备三档
- **30 秒**：一句话说清"是什么 + 技术栈 + 一个亮眼数字"。
- **3 分钟**：架构图 + 一条完整的请求链路（登录→匹配→出牌→结算）+ 一个你解决的难点。
- **10 分钟**：加演进的弯路（单进程→拆服务）、压测与优化前后对比、失败尝试。

## 9. 反模式（明确不要做）

1. ❌ 从零写游戏引擎 / 渲染 / 物理 —— 与后端岗无关。
2. ❌ 第一版就上微服务、K8s、服务网格 —— 会死于运维，且面试官一眼看出不是你的真实场景。
3. ❌ 用现成框架（如 skynet/pomelo 类）当主体 —— 你就只是在调 API。
4. ❌ 做 3D/FPS 实时对战 —— 复杂度错配。
5. ❌ 只写代码不写文档 —— 面试官看不到架构图，项目价值打对折。
6. ❌ 堆功能不做压测 —— 没有数字就没有说服力。
7. ❌ 长期不开源/不提交 —— 要有一个持续提交的公开仓库。

## 11. 本周就能开始的 5 件事

1. `git init`，建目录骨架（见下），第一个 commit。

```
│   ├── logic/                    # 纯玩法逻辑（零网络依赖，可单测）
│   ├── room/                     # 房间 actor 与调度
│   ├── persist/                  # MySQL 连接池、Redis 客户端
│   ├── gateway/                  # 网关进程
│   ├── match/                    # 匹配进程
│   └── server/                   # main 与装配
├── tests/                        # GoogleTest
├── bench/                        # 压测客户端
├── client/cli/                   # 终端客户端（关键路径，先进这个）
├── client/godot/                 # Godot 4.5 客户端（周末支线，见 ADR 0002）
└── deploy/                       # docker-compose、prometheus、grafana
```

**最重要的分层原则：`logic/` 不包含任何网络、数据库、线程代码。**
纯逻辑可单测 → 这是你能 2 周写完玩法、并且能在面试里讲"业务与基础设施解耦"的根本原因。
