# ADR 0002：客户端采用 Godot 4.5，服务端保持纯 C++

- 状态：已采纳
- 日期：项目启动期（修订 ADR 0001 第 2 条）
- 决策者：项目负责人
- 修订关系：**本 ADR 取代 ADR 0001 中的「客户端不引入引擎」一条，其余各条继续有效。**

## 背景

ADR 0001 原决定客户端不引入引擎（终端 → 网页）。项目负责人决定改用 Godot。
本 ADR 记录这个决定、它带来的代价，以及为保护进度而设置的四道护栏。

## 决策

**Godot 4.5 只做客户端的表现层（"壳"），服务端 100% 保持纯 C++。**

Godot 在本项目中的职责，严格限定为三件事：

1. 把服务端下发的**事件序列**渲染成画面（区域圆点、卡牌方框、战报滚动）。
2. 收集玩家的**意图**（点哪个区域、出哪张牌），打包成协议帧发给服务端。
3. 播放结算动画。

**它不负责：规则判定、随机数、状态权威、胜负计算——一行都不许有。**

## 四道护栏（任何一条被突破，本项目就完不成）

### 护栏一：Godot 永远不进关键路径

服务端必须先有**终端 CLI 客户端**（~5h 工时），能在纯文本下打完一整局。
Godot 客户端是**周末支线**，进度落后不影响服务端推进。

```
关键路径：逻辑层 → 单测 → 终端 CLI → 网络层 → 房间 → 压测
支线（周末 2h）：Godot 学习 → Godot 客户端
```

理由：如果"学 Godot"卡住关键路径，你会连续 3 周没有任何服务端进展，第 4 周就放弃了。**能在终端里玩 → 服务端永远有进展 → 项目不容易死。**

### 护栏二：GDScript 里不许出现游戏规则

判断标准：**把 Godot 客户端整个删掉，服务端是否仍然完全正确？** 必须能回答"是"。

具体禁止：
- ❌ 客户端判断"这张牌能不能出"
- ❌ 客户端算战力、算胜负
- ❌ 客户端生成随机数
- ❌ 客户端维护"我以为的"游戏状态（只维护"服务端告诉我的"状态）

### 护栏三：工时硬上限 70 小时

| 项 | 预算 |
|---|---|
| Godot 学习（Control 节点、signal、Resource、StreamPeerTCP） | ≤30h |
| 客户端实现 | ≤40h |
| **合计** | **≤70h（约 14 周）** |

**超了立刻退回网页客户端**（HTML + Canvas，25h）。这不是威胁，是止损线：
到第 30 小时还画不出"5 个圆点 + 一排卡牌 + 能发一条指令"，说明要么教程选错了，要么该换方案。

### 护栏四：不使用 Godot 的内置多人 API

- ❌ `MultiplayerAPI` / `ENetMultiplayerPeer` / 高层 RPC —— 它们绑定 Godot 自己的 ENet 协议，和我们的 C++ 服务端对不上。
- ❌ `WebSocketPeer` 做**服务端** —— Godot 只有 WS 客户端，没有 WS 服务端。
- ✅ 客户端用 `StreamPeerTCP` 直连 C++ 服务端，帧格式自己定。
- ✅ 服务端用 `TCPServer` 之上的 epoll Reactor（自研）。

## 技术选择

| 项 | 选择 | 理由 |
|---|---|---|
| 版本 | **Godot 4.5**（不要 3.x） | GDScript 2.0 与 3.x 不兼容，网上 3.x 教程会坑你 |
| 语言 | **GDScript** | 客户端只做表现，不需要 C++ 性能；C# 会引入第二套构建 |
| UI 节点 | `Control` 家族（`Panel`/`Button`/`Label`/`VBoxContainer`/`GridContainer`） | 回合制棋盘 = 一堆按钮，不需要 2D/3D 渲染管线 |
| 地图表现 | 5 个 `Button` 摆成环形，用 `Line2D` 或 `TextureRect` 画邻接线 | 别做 TileMap，别做寻路 |
| 网络 | `StreamPeerTCP` + 长度前缀帧 | 最简单，无需在 C++ 侧实现 RFC6455 |
| 数据表达 | 正式走二进制；调试期可临时用 JSON | 见护栏二上方原则 |
| 禁用 | GDExtension / Godot 的 C++ 绑定 | 会把 C++ 编译链拖进客户端，纯亏 |

## 必须做的一件事：传输层与协议层解耦

服务端把「帧怎么在线上跑」和「帧里装什么」分成两层：

```
[业务协议]  cmd + seq + payload         ← 与传输无关
[传输适配]  TCP 长度前缀  |  WebSocket 帧  ← 可替换
```

为什么这不是过度设计：**如果以后想出"网页可玩的 demo"，Godot 可以导出 Web，
但浏览器里没有裸 TCP，只能走 WebSocket。** 那时你只需要补一个 200 行的 WS 编解码外壳。

这条也是面试可讲的点："我的协议与传输解耦，后来加 WebSocket 支持只改了一个外壳，业务代码零改动。"

## 代价（诚实记账）

| 项 | 网页客户端方案 | Godot 方案 | 差额 |
|---|---|---|---|
| 客户端工时 | 25h | 70h | **+45h ≈ +9 周** |
| 学习成本 | 几乎为零 | 约 30h | 吃掉 6 周 |
| 可分享 demo | 一个链接 | 需导出 Web + WS | Godot 更麻烦 |
| 观感 | 朴素 | **好很多** | 唯一实质收益 |

**时间线影响：联网可投简历的节点从 ~6 个月推到 ~8 个月，完整作品从 ~10 个月推到 ~12 个月。**

## 收益（为这个决定找的合理依据）

1. **观感确实好很多**——回合制棋盘游戏用 Control 节点做界面非常快，能做出"像个真游戏"的演示，README 里的 GIF 会好看很多。
2. **如果投游戏公司后端岗**（网易/米哈游/腾讯游戏/莉莉丝），"我自己写了个 Godot 客户端"能证明你懂客户端的处境，协作时少扯皮。这是真实的小加分。
3. **跨语言协议联调**本身就是一段经历：C++ 服务端 ↔ GDScript 客户端，字节序、编码、粘包、断线，全都要真的处理对。
4. **动机价值**：一个能看的游戏比一个终端程序更能让你坚持 12 个月。这一条无法量化，但对个人项目可能是最重要的。

## 后果

- 关键路径不变，但 M2 完成时间推迟约 9 周。
- 多一套工具链要维护（Godot 项目 + C++ 工程），但两者只通过协议通信，耦合很松。
- 简历技能栏可以写 Godot 4.5 / GDScript（对后端岗几乎不加分，但对游戏行业岗位有微弱的正面作用）。

## 复审条件

1. Godot 学习超过 30h 仍画不出基本界面 → 退回网页客户端。
2. 客户端累计 70h 仍未打通"登录→开局→出一张牌"→ 退回网页客户端。
3. 发现自己在 GDScript 里写规则判定 → 立即删除，回到护栏二。
