# ADR 0001：不引入游戏引擎，明确自研边界

- 状态：**部分已修订**（第 2 条「客户端不引入引擎」已被 [ADR 0002](0002-godot-client.md) 取代；第 1、3 条及自研边界表继续有效）
- 日期：项目启动
- 决策者：项目负责人

## 背景

项目是「4 人混战、回合制、同时决策」的抢地游戏，目标是作为**后端工程师求职的主项目**。
需要回答两个问题：① 服务端要不要用游戏引擎/游戏服务器框架？② 客户端要不要用引擎？

## 决策

1. **服务端不引入任何游戏引擎或游戏服务器框架**（skynet / pomelo / Photon / NoahGameFrame 等）。
2. **客户端不引入引擎**，按「终端 → 网页」两阶段推进，不进入「桌面应用/3D」形态。
3. **自研边界严格按下表执行**，不越界也不重复造轮子。

## 自研边界

### 必须自己写（这是项目的简历价值所在）

| 模块 | 为什么必须自研 |
|---|---|
| epoll Reactor 网络层 | C++ 后端面试的核心考点，用库等于把最值钱的部分外包 |
| 应用层协议（帧格式、编解码、粘包处理） | 面试必问，且决定后面所有扩展 |
| 房间调度（actor-per-room + SPSC 队列） | 并发模型的设计能力，无法用库替代 |
| 结算器（确定性战斗算式 + 随机种子） | 业务核心，也是"可回放"的基础 |
| AI（托管 / 补位 / 单机对手） | 一个模块三处复用，体现工程判断 |
| MySQL 连接池 | 小而有代表性，20 行接口 + 100 行实现 |
| 状态裁剪下发（每人只看自己那份） | 多人游戏的核心坑，教科书里没有 |

### 直接用现成的（重复造轮子不加分，反而减分）

| 领域 | 用什么 | 理由 |
|---|---|---|
| 构建 | CMake + Ninja | 事实标准 |
| 依赖管理 | vcpkg 或 CMake FetchContent | 别手搓下载脚本 |
| 日志 | spdlog | 自己写异步日志是另一门课，本项目不需要 |
| 测试 | GoogleTest + CTest | 有单测的学生项目已经是少数 |
| 数据库驱动 | MySQL Connector/C、hiredis | 驱动层没有学习价值 |
| HTTP/序列化（若需要） | protobuf / nlohmann-json | 协议设计的学习点在手写部分 |
| 前端 | 原生 HTML + CSS + Canvas + 原生 WebSocket | 300 行足够，不引框架 |

> 判断标准：**这一层能否在面试中被追问 5 分钟？** 能 → 自研；不能 → 用库。
> "我把什么都自己写了一遍"不是加分项，是工程判断力缺失的信号。

## 客户端路线

| 阶段 | 形态 | 工时 | 用途 |
|---|---|---|---|
| A（M1 期间） | 终端 TUI：ASCII 地图 + 文本指令 + 战报滚动 | ~5h | 自己试玩调平衡，不接网络，逻辑层直接链接 |
| B（M2 后期） | 单页网页：5 个区域画成圆点，卡牌画成方框，WebSocket 连接，战报列表滚动 | ~25h | 可分享的 demo URL，放简历 |
| C（可选，不计划做） | Godot / Unity 换皮 | 不估 | 只有当想转客户端岗时才考虑 |

**客户端总工时硬上限 30 小时。** 超了就是设计问题，回来砍界面，不要砍服务端。

## 为什么不上 Unity / Unreal

1. **没有图形需求**：回合制、事件回放、UI 为主，没有 3D、没有物理、没有实时渲染管线。
2. **会吃掉你的时间预算**：UE 的 C++ 意味着 UObject、GC、模块系统、蓝图与 C++ 边界、打包流程——这些概念对后端岗几乎不加分，却会占掉本项目 50% 以上的工时。
3. **求职错配**：目标是后端工程师。客户端多花的每一小时，都是从 epoll、协议设计、压测里偷走的。
4. **意外好处**：不引入引擎，你的"服务端权威 + 事件回放"架构才成立——客户端只负责播，没有本地权威逻辑可被篡改。

**唯一例外**：如果目标是游戏客户端 / 引擎岗，这个决策需要重写。

## 如果要"借力"，借在设计而不是代码

- 读 **muduo** 源码（陈硕的 C++ 网络库）：`one loop per thread` 的 Reactor 结构、`Buffer` 的读写法、`TcpConnection` 的生命周期管理。这是 C++ 后端面试的经典加分项，读完自己实现一遍，比直接用强一百倍。
- 读 **skynet** 的 actor 调度思路（不必读完全部）。
- 读 **libevent / libuv** 的事件循环抽象，理解跨平台 poller 接口怎么设计。

产出一份 `docs/reading-notes-muduo.md`，面试时能直接讲"我参考它的设计，但我做了 X 不同的取舍"。

## 后果

- 好处：技术栈极薄，几乎零学习成本；所有工时都花在面试考点上；6 个月内能出联网版本。
- 代价：没有"漂亮的画面"；如果有人用 Unity 做了个炫酷 demo，短期观感会被比下去。
- 缓解：第 12 周写一个网页客户端，配合演示 GIF 放进 README，观感问题基本解决。

## 什么情况下推翻这个决策

1. 目标岗位从后端改成游戏客户端 / 引擎 → 重写本 ADR。
2. 玩法演化成需要实时渲染的形态（如 3D 战场） → 说明设计走偏了，先砍回回合制，而不是引入引擎。
